Section 01

TicketIQ — System Architecture & Design Specification

This document details the complete end-to-end architecture, database schema, API contracts, data flows, and project folder layout for TicketIQ, an AI IT-helpdesk triage and resolution assistant.

1. High-Level System Architecture

TicketIQ separates user-facing ticket management from machine learning inference and retrieval-augmented generation (RAG) while unifying relational ticket data and dense vector embeddings inside PostgreSQL using the pgvector extension.

2. Core Components

  1. Flutter Web Dashboard (Client Tier):
    - Support agent view: Live queue filtered by priority and category, auto-triage confirmation badge, similar tickets pane, and one-click RAG fix insertion.
    - User view: Ticket submission form with instant feedback.
  2. FastAPI Application (Application Tier):
    - Security: OAuth2 Password Bearer with JWT tokens (user, agent, admin roles).
    - Ticket Manager: Standard CRUD for tickets, statuses, assignments, and audit logs.
    - Inference Engine: Loads pre-trained all-MiniLM-L6-v2 encoder (via sentence-transformers) and serialized Scikit-learn Logistic Regression models (category_model.joblib, priority_model.joblib).
    - RAG Chain Manager: LangChain orchestrator that binds retrieved context into an explainable prompt template and invokes Gemini 1.5 Flash with structured Pydantic output.
  3. Supabase PostgreSQL with pgvector (Data Tier):
    - Relational tables for Users and Tickets.
    - Dense vector column embedding vector(384) storing ticket textual representations.
    - HNSW index on embedding using vector_cosine_ops for fast approximate nearest neighbor (ANN) cosine distance queries.
  4. Google Gemini 1.5 Flash (LLM Provider):
    - Free-tier hosted LLM accessed via langchain-google-genai.
    - Constrained via structured JSON output parser to return strictly {suggested_fix, sources, confidence_note} without hallucinations.

3. Data Flows

Flow 1: Ticket Ingestion & Auto-Triage (POST /api/v1/tickets)

  1. User or agent submits {title, description}.
  2. Embedding Service computes dense vector: (\mathbf{v} \in \mathbb{R}^{384}).
  3. Triage Classifier feeds (\mathbf{v}) into Logistic Regression models to predict:
    - category (e.g., Hardware, Software, Network, Access)
    - priority (e.g., Low, Medium, High, Critical)
  4. Ticket record is inserted into tickets table with status = 'Open', predicted labels, and embedding = v.
  5. Created ticket is returned with HTTP 201.
sequenceDiagram autonumber actor User as Client / User participant API as FastAPI Router participant ML as ML Triage Service participant DB as PostgreSQL (pgvector) User->>API: POST /api/v1/tickets (title, description) API->>ML: Predict category & priority (all-MiniLM-L6-v2 + LogReg) ML-->>API: Predicted labels & probability distributions API->>ML: Compute vector embedding (384-dim) ML-->>API: Dense vector embedding API->>DB: INSERT into tickets (title, desc, category, priority, embedding, status='Open') DB-->>API: Inserted Ticket Record API-->>User: HTTP 201 Created (Ticket Details + Predicted Triage)

Flow 2: Similar / Duplicate Ticket Search (POST /api/v1/tickets/similar)

  1. Agent inputs text query or references an active ticket ID.
  2. Text is converted to embedding (\mathbf{q} \in \mathbb{R}^{384}).
  3. Query executes cosine distance lookup in PostgreSQL:
    sql SELECT id, title, description, status, resolution_notes, 1 - (embedding <=> :q) AS similarity_score FROM tickets WHERE id != :exclude_id ORDER BY embedding <=> :q ASC LIMIT :limit;
  4. Returns top-K similar historical tickets with similarity scores (\in [0, 1]).

Flow 3: RAG Resolution Assistant (POST /api/v1/tickets/{id}/suggest)

  1. Agent requests AI resolution assistance for ticket ID (t).
  2. System fetches ticket (t) and retrieves top-3 historically Resolved tickets with cosine similarity score (\ge 0.65).
  3. If no resolved tickets meet the threshold, chain halts early and returns a fallback message: "No sufficiently similar resolved tickets found. Please escalate to a Senior Specialist."
  4. If similar resolved tickets exist, format context into a strict prompt template:
    - Grounding rule: Use only historical resolutions. Do not invent steps.
  5. Invoke Gemini 1.5 Flash with structured output schema:
    json { "suggested_fix": "Step-by-step resolution steps...", "sources": [102, 189], "confidence_note": "Based on 2 historical tickets with >80% similarity." }
  6. Return structured JSON payload to the agent dashboard.

-- Enable pgvector extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Users table
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) UNIQUE NOT NULL,
    hashed_password VARCHAR(255) NOT NULL,
    full_name VARCHAR(255) NOT NULL,
    role VARCHAR(50) NOT NULL DEFAULT 'user' CHECK (role IN ('user', 'agent', 'admin')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Tickets table
CREATE TABLE tickets (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title VARCHAR(255) NOT NULL,
    description TEXT NOT NULL,
    category VARCHAR(50) NOT NULL CHECK (category IN ('Hardware', 'Software', 'Network', 'Access')),
    priority VARCHAR(50) NOT NULL CHECK (priority IN ('Low', 'Medium', 'High', 'Critical')),
    status VARCHAR(50) NOT NULL DEFAULT 'Open' CHECK (status IN ('Open', 'In_Progress', 'Resolved', 'Closed')),
    created_by_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    assigned_to_id UUID REFERENCES users(id) ON DELETE SET NULL,
    resolution_notes TEXT,
    embedding VECTOR(384),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Standard relational indexes
CREATE INDEX idx_tickets_status ON tickets(status);
CREATE INDEX idx_tickets_category ON tickets(category);
CREATE INDEX idx_tickets_priority ON tickets(priority);
CREATE INDEX idx_tickets_created_by ON tickets(created_by_id);
CREATE INDEX idx_tickets_assigned_to ON tickets(assigned_to_id);

-- HNSW Vector Index for Cosine Distance (<=>)
-- m=16 (connections per element), ef_construction=64 (build trade-off)
CREATE INDEX idx_tickets_embedding_hnsw 
ON tickets USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

5. API Contracts & Specifications

All authenticated endpoints require an Authorization: Bearer <JWT> header.

5.1 Authentication Endpoints

  • POST /api/v1/auth/register: Create a new user account.
  • POST /api/v1/auth/login: Exchange username & password for {access_token, token_type}.
  • GET /api/v1/auth/me: Retrieve current user profile and role.

5.2 Ticket Management Endpoints

  • POST /api/v1/tickets:
  • Request: { "title": "Cannot connect to VPN", "description": "GlobalProtect gives error 502." }
  • Response (201): Ticket object including auto-predicted category, priority, and status: "Open".
  • GET /api/v1/tickets: List tickets with query params (status, category, priority, limit, offset).
  • GET /api/v1/tickets/{id}: Detailed ticket view.
  • PATCH /api/v1/tickets/{id}: Update status, assignment, or resolution notes.

Phase 1: Standalone ML Classifier & Experimentation Notebook

Estimated Timeline: Days 1 – 6

Goal

Build, rigorously evaluate, and compare an explainable text classification pipeline predicting ticket Category (multiclass) and Priority (multiclass/ordinal) from textual descriptions using Scikit-Learn.

Tasks

  1. Data Acquisition & EDA:
    - Download the IT/Customer Support Ticket dataset from Kaggle into data/raw/.
    - Perform exploratory data analysis: inspect distributions of ticket lengths, class frequencies for Category (Hardware, Software, Network, Access) and Priority (Low, Medium, High, Critical).
    - Clean text: lowercase conversion, whitespace normalization, removal of HTML tags/system artifacts.
  2. Train/Test Splitting:
    - Create a clean 80/20 train/test split using StratifiedShuffleSplit to preserve class distributions across both Category and Priority.
    - Set aside a 100-ticket held-out set specifically for future retrieval benchmarking in Phase 2.
  3. Baseline Model (TF-IDF + Logistic Regression):
    - Fit TfidfVectorizer (max_features=5000, n-gram range=(1, 2), stop_words='english') on training text.
    - Train LogisticRegression(max_iter=1000, class_weight='balanced') for Category and Priority.
    - Evaluate with classification_report (precision, recall, macro-F1) and confusion matrices.
  4. Embedding-Based Model (all-MiniLM-L6-v2 + Logistic Regression):
    - Generate 384-dimensional dense sentence embeddings using sentence-transformers.
    - Train LogisticRegression on the dense embeddings.
    - Compare performance against the TF-IDF baseline using Macro-F1.
  5. Model Serialization:
    - Save the fitted vectorizer/embedder config and trained Logistic Regression estimators using joblib into data/models/.

Deliverables

  • notebooks/01_eda_and_cleaning.ipynb
  • notebooks/02_baseline_tfidf_logistic_regression.ipynb
  • notebooks/03_embeddings_logistic_regression.ipynb
  • Serialized artifacts: data/models/embedding_category_lr.joblib, data/models/embedding_priority_lr.joblib, data/models/label_encoders.joblib.
  • Experiment log table comparing TF-IDF vs Dense Embeddings.

Acceptance Criteria

  • [ ] Category classifier achieves (\ge 0.75) Macro-F1 on the test set.
  • [ ] Priority classifier achieves (\ge 0.65) Macro-F1 on the test set.
  • [ ] Embedding-based classifier matches or outperforms the TF-IDF baseline.
  • [ ] Confusion matrices generated and analyzed for systematic confusion (e.g. Medium vs High priority).
  • [ ] Serialized .joblib models can be loaded into a clean Python session and produce predictions on raw strings in (< 25\text{ ms}).

Phase 2: Vector Search & Grounded Retrieval with pgvector

Estimated Timeline: Days 7 – 12

Goal

Set up Supabase PostgreSQL with the pgvector extension, batch-index ticket embeddings, and build an explainable similarity search pipeline evaluated on a held-out benchmark.

Tasks

  1. Database Vector Initialization:
    - Enable vector extension in Supabase PostgreSQL instance.
    - Define table schema for tickets with column embedding vector(384).
    - Create an HNSW index using cosine distance: USING hnsw (embedding vector_cosine_ops).
  2. Batch Ingestion Script:
    - Write a standalone Python script scripts/ingest_historical_tickets.py to embed historical resolved tickets and bulk-insert them into Supabase via SQLAlchemy.
  3. Similarity Search Implementation:
    - Write SQL queries computing Cosine Similarity from Cosine Distance:
    [
    \text{Cosine Similarity} = 1 - (\mathbf{u} \cdot \mathbf{v}) = 1 - (\text{embedding} \Leftrightarrow \text{query_vector})
    ]
    - Implement filtering by status = 'Resolved' and similarity thresholding ((\ge 0.65)).
  4. Retrieval Evaluation (Hit@3 Benchmark):
    - Run retrieval against the 100 held-out evaluation tickets.
    - For each evaluation ticket, retrieve top-3 similar tickets.
    - Compute Hit@3: percentage of queries where at least one of the top-3 retrieved tickets addresses the same root cause category.

Deliverables

  • notebooks/04_pgvector_retrieval_and_eval.ipynb
  • scripts/ingest_historical_tickets.py
  • Supabase SQL schema migration script.
  • Retrieval evaluation report documenting Hit@3 and average query latency.

Acceptance Criteria

  • [ ] Supabase table populated with (\ge 1,000) embedded historical tickets.
  • [ ] HNSW vector index active and functional.
  • [ ] Retrieval query latency (< 100\text{ ms}) for top-3 nearest neighbors.
  • [ ] Hit@3 metric on the 100-ticket held-out set achieves (\ge 80\%).

TicketIQ — Production Risks & Mitigation Strategies

This document identifies the 5 primary risks in building TicketIQ — spanning dataset quality, statistical class imbalance, LLM hallucinations, free-tier limits, and vector dimensional integrity — alongside concrete engineering mitigations.

Risk Matrix Summary

# Risk Area Severity Likelihood Key Mitigation
1 Dataset Quality & Noisy Resolutions High High Strict data cleaning pipeline: length thresholding & removal of boilerplate resolutions
2 Class Imbalance in Category & Priority High High Stratified train/test splitting, class_weight='balanced', and Macro-F1 evaluation
3 LLM Hallucination in Technical Fixes Critical Medium Similarity gating ((\ge 0.65)), strict prompt grounding, and Pydantic structured output
4 Free-Tier API & Cloud Rate Limits Medium High In-memory LRU caching, Supabase transaction pooling, and graceful backoff
5 Vector Dimension & Distance Metric Mismatch High Low Explicit DDL constraints (vector(384)), (L_2) normalization, and cosine distance <=>

Detailed Risk Analysis & Mitigations

1. Dataset Quality & Missing Ticket Resolution Text

The Risk

Public IT support datasets from Kaggle often contain incomplete rows, placeholder descriptions ("Help, my screen is blue"), or meaningless resolution notes ("Resolved by user", "Issue closed", "N/A"). If these low-quality records are indexed in the vector store, similarity searches will retrieve irrelevant records, and the RAG model will generate useless or corrupt recommendations.

Engineering Mitigations

  1. Resolution Quality Filter:
    - In Day 2 preprocessing, discard any historical ticket where resolution_notes is null, has fewer than 25 characters, or matches common boilerplate regexes:
    python boilerplate_patterns = [r"^resolved", r"^fixed", r"^closed", r"^ticket closed", r"^n/a$"]
  2. Text Normalization Pipeline:
    - Clean both titles and descriptions: strip HTML tags, normalize whitespace, lowercase text, and remove non-informative ticket IDs or automated email headers.
  3. Curated Historical Index:
    - Only index tickets marked with status = 'Resolved' that have verified, substantive resolution notes.

2. Severe Class Imbalance (Category & Priority)

The Risk

In real helpdesk data, categories and priorities are heavily skewed:
- Priorities: ~65% Low, ~25% Medium, ~8% High, ~2% Critical.
- Categories: ~50% Software, ~30% Hardware, ~15% Network, ~5% Access.

A standard classifier optimizing for naive accuracy will predict the majority class (Low / Software) for all tickets, achieving ~65% accuracy while completely failing on Critical or Access tickets.

Engineering Mitigations

  1. Stratified Splitting:
    - Use StratifiedShuffleSplit in Scikit-Learn to ensure that train and test partitions maintain identical class distributions for both Category and Priority.
  2. Class-Weighted Loss Optimization:
    - Configure Scikit-Learn's LogisticRegression(class_weight='balanced'). This automatically adjusts weights inversely proportional to class frequencies:
    [
    w_j = \frac{N}{K \cdot n_j}
    ]
    where (N) is total samples, (K) is number of classes, and (n_j) is the sample count of class (j). Errors on minority classes (Critical) are penalized far more heavily during gradient descent.
  3. Metric Alignment:
    - Reject accuracy as a primary metric. Use Macro-averaged F1 Score, which computes the arithmetic mean of F1 scores across each class independently, treating minority and majority classes with equal weight.

3. LLM Hallucination & Ungrounded Resolutions

The Risk

LLMs given loose prompts will attempt to be helpful by inventing IT procedures, non-existent terminal commands, or insecure password reset links. In an IT enterprise setting, an invented or incorrect command can cause system downtime or data loss.

Engineering Mitigations

  1. Similarity Score Gating (Pre-LLM Guardrail):
    - Before invoking Gemini, inspect the cosine similarity score of the top retrieved historical ticket.
    - If top_similarity < 0.65, do not invoke the LLM. Immediately return a deterministic fallback response:
    json { "suggested_fix": "No sufficiently similar historical resolution found (similarity < 0.65). Please escalate this ticket to a Tier-2 IT Specialist.", "sources": [], "confidence_note": "Below automated resolution threshold." }
  2. Strict Grounding Prompt Template:
    - Instruct the LLM that it is an administrative assistant summarizing verified records, strictly forbidding external facts:
    text You are an IT resolution assistant. You are provided with 3 historically resolved tickets. Synthesize a clear, step-by-step fix ONLY using the historical resolutions provided. Do NOT add outside knowledge, do NOT invent commands, and do NOT assume software versions. If the provided resolutions do not clearly solve the user's issue, state: "Historical data is insufficient to resolve this issue."
  3. Structured Pydantic Enforcement:
    - Use with_structured_output to require the LLM to return source ticket IDs in the sources field. If the model cannot cite an ID from the context, the response is rejected.

4. Free-Tier API Rate Limits & Cloud Resource Constraints

The Risk

  • Google Gemini API: Free tier enforces a strict limit of 15 Requests Per Minute (RPM). Rapid testing or multi-user interaction can trigger HTTP 429 errors.
  • Supabase Free Tier: Free compute allows limited concurrent direct database connections (often 60 pooler / direct connections).
  • Render Web Service Free Tier: Free web services spin down after 15 minutes of inactivity, resulting in a 30–50 second cold start delay.

Engineering Mitigations

  1. In-Memory Embedding Caching:
    - Implement an LRU cache (@lru_cache(maxsize=1024)) in the embedding service so repetitive queries (e.g. duplicate search terms) return cached 384-dim vectors without recomputing.
  2. Local Model Inference:
    - All classification (LogisticRegression) and sentence encoding (all-MiniLM-L6-v2) runs locally on the CPU in Python. No external API quotas are consumed for classification or vector generation.
  3. Exponential Backoff for Gemini Calls:
    - Wrap the LangChain Gemini call with retry logic (using tenacity) that handles HTTP 429 rate limits gracefully with exponential backoff and jitter.
  4. Supabase Connection Pooling (Transaction Mode):
    - Direct all backend database queries through Supabase PgBouncer (port 6543) instead of direct port 5432. This reuses database connections across stateless FastAPI requests.

5. Vector Dimension & Distance Metric Mismatch

The Risk

A common defect in vector applications is initializing the database column with the wrong dimension (e.g. vector(1536) intended for OpenAI models instead of vector(384) for all-MiniLM-L6-v2), or querying with Euclidean distance (<->) when the vectors are compared using cosine similarity.

Engineering Mitigations

  1. Explicit Schema Typing:
    - Define the PostgreSQL column strictly as embedding vector(384) in Alembic migrations.
  2. Vector Normalization:
    - Ensure sentence-transformers generates (L_2)-normalized vectors:
    python model.encode(text, normalize_embeddings=True)
    - When vectors have unit length ((|\mathbf{u}|_2 = 1)), Cosine Distance is directly proportional to Euclidean distance:
    [
    |\mathbf{u} - \mathbf{v}|_2^2 = 2(1 - \mathbf{u} \cdot \mathbf{v})
    ]
  3. Dedicated Unit Tests:
    - Include an automated Pytest verifying that the vector output of encoder.py always returns an array of shape (384,) with unit magnitude before inserting into the database.

2. Interview Defense Cheat-Sheet (High-Yield Q&A)

Q1: "Why did you use Logistic Regression with sentence embeddings instead of fine-tuning a BERT model or calling an LLM for classification?"

Your Answer:

"I deliberately chose Logistic Regression on top of frozen sentence embeddings (all-MiniLM-L6-v2) for three engineering reasons:
1. Inference Latency & Cost: Calling an LLM for triage adds 1–2 seconds of network latency and token costs per ticket. A Logistic Regression model runs in under 25 milliseconds directly on CPU with zero API costs.
2. Explainability & Probabilities: Logistic Regression outputs well-calibrated class probability distributions via the Softmax function. This allows our backend to assign confidence scores to predictions and flag low-confidence tickets for manual agent review.
3. Sample Efficiency & Defense: Fine-tuning a full transformer with limited IT helpdesk data easily leads to overfitting. Using a high-quality pretrained sentence encoder as a fixed feature extractor and fitting a convex loss function (cross-entropy with L2 regularization) guaranteed fast convergence, explainable decision boundaries, and no GPU requirements."

Q2: "How did you handle the severe class imbalance in ticket priorities?"

Your Answer:

"Priority distribution in helpdesk logs is naturally skewed—Low and Medium tickets account for over 85% of samples, while Critical tickets are under 3%. If you optimize for standard accuracy, a trivial model predicting 'Low' achieves high accuracy while failing completely on critical outages.
I addressed this systematically:
1. I used Stratified Splitting (StratifiedShuffleSplit) to ensure both train and test partitions reflected the true distribution.
2. I configured balanced class weighting in the Logistic Regression cost function. This weights the cross-entropy loss inversely proportional to class frequencies: (w_j = \frac{N}{K \cdot n_j}). Penalizing errors on minority classes heavily during gradient descent prevented the decision boundaries from collapsing toward the majority class.
3. I evaluated the model using Macro-averaged F1 rather than accuracy or Micro-F1, giving equal importance to Critical and Low classes."

Q3: "Why did you store embeddings in PostgreSQL with pgvector instead of using a standalone vector DB like Pinecone, Chroma, or Weaviate?"

Your Answer:

"In a production IT helpdesk system, tickets are relational entities with foreign keys (requesters, assignees), audit logs, and strict state transitions (Open (\to) In Progress (\to) Resolved).
Using a dedicated vector database creates an operational two-system problem: you have to synchronize relational updates in PostgreSQL with vector updates in Pinecone, risking data drift and requiring distributed transaction handling.
With pgvector, our embeddings live directly inside the tickets table as a vector(384) column. We can execute a single ACID transaction that updates a ticket's status and re-indexes its embedding simultaneously, and perform filtered nearest-neighbor queries using standard SQL with HNSW index performance."

Q4: "How did you objectively evaluate your retrieval system before feeding context into the LLM?"

Your Answer:

"I did not rely on subjective inspection. I constructed a dedicated 100-ticket held-out evaluation set (eval_100_heldout.csv) from historical resolved tickets.
I evaluated the retriever using Hit@3: for each test ticket description, we executed an automated vector query retrieving the top-3 historical matches and checked whether at least one retrieved ticket matched the ground-truth root cause category and had an actionable resolution.
TicketIQ achieved an [86%] Hit@3 rate. Furthermore, we benchmarked retrieval latency using EXPLAIN ANALYZE on Supabase to verify that HNSW index searches executed in under 100 milliseconds."

Q5: "How did you guarantee that the LLM wouldn't hallucinate fake terminal commands or dangerous IT procedures in the resolution suggestion?"

Your Answer:

"We implemented a 3-layer defense against hallucinations:
1. Pre-LLM Similarity Gating: Before calling the LLM, we check the cosine similarity of the top retrieved historical ticket. If it is below 0.65, we abort the LLM call entirely and return a deterministic message advising human escalation. We never ask an LLM to generate answers when historical context is absent.
2. Strict Grounding Prompt: Our system prompt explicitly defines the LLM as a synthesizer of provided records, strictly forbidding the introduction of outside facts or unverified commands.
3. Pydantic Schema Validation: Using LangChain's with_structured_output, the model is forced to return a JSON object containing a sources array citing the exact historical ticket IDs used. If the model fails schema validation or cannot cite sources, the response is rejected."

1. Core Architectural Decisions & Mathematical Defenses

Decision 1: Logistic Regression + Pretrained Embeddings vs. LLM / Transformer Fine-Tuning

  • What We Did: We used frozen 384-dimensional sentence embeddings (all-MiniLM-L6-v2) paired with Scikit-Learn LogisticRegression (with a TF-IDF baseline).
  • The Mathematical Reality:
  • Sentence embeddings map raw text into a normed metric space (\mathbf{x} \in \mathbb{R}^{384}) where semantic similarity corresponds to geometric proximity ((\cos \theta)).
  • Logistic Regression fits a linear decision boundary in this 384-dimensional space by optimizing the convex cross-entropy (log-loss) objective:
    [
    J(\mathbf{w}) = -\frac{1}{N} \sum_{i=1}^N \sum_{k=1}^K y_{ik} \log \left( \frac{e^{\mathbf{w}_k^T \mathbf{x}i}}{\sum{j=1}^K e^{\mathbf{w}_j^T \mathbf{x}_i}} \right) + \frac{1}{2C} |\mathbf{w}|_2^2
    ]
  • Interview Defense (Why NOT fine-tune a BERT model or call Gemini for triage?):

    "Fine-tuning a transformer on 2,000–5,000 helpdesk tickets easily leads to catastrophic forgetting and severe overfitting. Moreover, invoking an LLM API for every incoming ticket introduces 1–2 seconds of network latency and non-zero dollar costs per query. By combining a frozen pretrained encoder with Logistic Regression, our inference runs in <25 ms on standard CPU, is completely cost-free, guarantees convex convergence, and outputs calibrated Softmax probabilities for confidence scoring."

Decision 2: Handling Severe Priority Class Imbalance (70% Low vs 2% Critical)

  • What We Did:
    1. Partitioned dataset using StratifiedShuffleSplit to guarantee identical class ratios in train and test splits.
    2. Applied inverse-frequency weighting in the loss function via class_weight='balanced'.
    3. Evaluated performance strictly via Macro-averaged F1 and Confusion Matrices instead of standard accuracy.
  • The Mathematical Reality:
  • The sample weight for class (j) is inversely proportional to its frequency:
    [
    w_j = \frac{N}{K \cdot n_j}
    ]
    Where (N) is total samples, (K) is number of classes, and (n_j) is the count of class (j).
  • During gradient descent, misclassifying a Critical ticket produces a gradient step (w_{\text{critical}} \approx 35 \times) larger than misclassifying a Low ticket, forcing the decision hyperplanes away from minority regions.
  • Interview Defense:

    "In production IT support, missing a Critical ticket causes massive SLA breaches. A naive model predicting 'Low' for all tickets achieves 70% accuracy but has zero utility. By weighting the cross-entropy loss inversely to class counts and validating against Macro-F1 (unweighted mean of per-class F1), we ensured the model generalizes equally well across rare outages and common queries."

Decision 3: Single Unified Database (Supabase PostgreSQL + pgvector) vs. Standalone Vector DBs

  • What We Did: We stored ticket relational metadata, user foreign keys, and 384-dim dense embeddings in a single PostgreSQL database using the pgvector extension with an HNSW index.
  • The Architectural Reality:
  • Using a standalone vector database (e.g. Pinecone, Chroma, Milvus) alongside PostgreSQL creates a dual-source-of-truth problem:
    1. Relational operations (ticket reassignment, status update from Open (\to) Resolved) must be synchronized with external vector store IDs.
    2. Network partitions cause data drift (ticket deleted in Postgres but still retrieved in Pinecone).
    3. Requires two separate connection pools and backup systems.
  • Interview Defense:

    "IT helpdesk tickets are fundamentally relational entities with strict ACID state transitions. pgvector allows us to perform dense vector similarity queries using the <=> cosine distance operator in the exact same SQL transaction that filters by status = 'Resolved'. We achieved <100 ms query latency using an HNSW index while maintaining single-database ACID guarantees and zero data drift."

Decision 4: Hallucination Guardrails in RAG Resolution

  • What We Did:
    1. Pre-LLM Similarity Gate: If the top retrieved ticket has cosine similarity (< 0.65), the chain aborts and returns an automated human-escalation message. Gemini is never called with weak context.
    2. Strict Grounding Prompt: System instructions strictly forbid outside knowledge and require the LLM to act solely as a summarizer of historical tickets.
    3. Pydantic Structured Output: LangChain's with_structured_output guarantees validated JSON containing a mandatory sources: list[int] field.
  • Interview Defense:

    "In an IT helpdesk context, hallucinating an incorrect terminal command or registry key can crash user systems. We treat LLMs not as knowledge repositories, but as reasoning engines over retrieved facts. If our vector search cannot find a historical ticket with (\ge 65\%) semantic similarity, we refuse to generate an answer and immediately route to a human engineer."

"What is the difference between Macro-F1 and Micro-F1?" "Micro-F1 aggregates global true positives, false positives, and false negatives, making it equivalent to accuracy in single-label multi-class settings—dominated by the majority class. Macro-F1 calculates the F1-score independently for each class and takes their unweighted arithmetic mean, treating rare Critical tickets as equally important as common Low tickets."
"What is the time complexity of vector search with HNSW?" "Exact k-NN search requires brute-force linear scanning: (\mathcal{O}(N \cdot d)), which is unacceptable at scale. HNSW (Hierarchical Navigable Small World) constructs a multi-layer graph where search is logarithmic: (\mathcal{O}(\log N \cdot d)), reducing latency to under 10 ms for 100k vectors."
"Why use Cosine Distance instead of Euclidean Distance?" "Euclidean distance ((L_2)) measures the straight-line distance between vector endpoints, which is sensitive to document length and magnitude. Cosine similarity measures the angle between vectors, capturing semantic orientation independent of length. When embeddings are (L_2)-normalized to unit length ((|\mathbf{u}|_2 = 1)), Cosine Distance is monotonically related to squared Euclidean distance: (|\mathbf{u} - \mathbf{v}|_2^2 = 2(1 - \mathbf{u} \cdot \mathbf{v}))."
"How did you prevent SQL injection and connection exhaustion in FastAPI?" "We used SQLAlchemy ORM with parameterized queries, eliminating SQL injection vectors. For database concurrency, we routed all connections through Supabase's PgBouncer transaction pooler (port 6543) so stateless FastAPI requests share a small pool of database sockets rather than opening a new connection per request."
"How did you test your RAG pipeline without spending API quota?" "In our Pytest suite, we mocked the external Gemini LLM client using unittest.mock and fixture dependency injection.
